# 项目简介

- **产品愿景:** 把内部财务团队每月面对的数百至数千行报销数据,收敛成真正需要人看的少数几十行 —— 且每一条判定都附带可追溯的制度条款逐字引用与原始数据行证据链。
- **目标用户:** 企业内部财务审核员(主)。技术水平中等(Excel 熟练、能理解规则配置、不写代码),风险规避型 —— 最担心的不是多花时间,而是「漏放了一张违规单」。次要角色:规则配置员 / 管理员、财务负责人(只读)。**明确不在 MVP 内:报销提交员工(无员工端界面)。**

## 核心定位(设计约束的来源)
- **单一客户交付,按可推广方式设计:** 当前为内部财务团队按生产系统标准建设,非 SaaS(无自助注册 / 计费 / 租户管理后台,单租户单机)。但所有本可硬编码之处(字段映射、规则阈值、制度条款)一律数据驱动,为第二家企业预留。
- **在有证据的地方泛化,没有证据的地方不泛化:** 例如阈值自动抽取技术可行,但因失败模式不可见(把 200 抽成 2000 静默放过违规单)刻意不做。
- **三个差异化能力空白:** 跨单据 / 跨员工关联分析、可解释证据链 + 条款级逐字引用、制度文档自适应。
- **形态:agent-in-workflow** —— 确定性 workflow 主干(可复现、可审计)+ 单点 ReAct 取证 agent。审计结论必须经得起内审质询,不能把整条链路交给概率性推理。

## 设计原则(UI)
1. **证据优先于结论** —— 任何判定在界面上都与其依据同屏呈现,不需额外点击才能看到理由。
2. **分级引导注意力** —— 界面服务于「先看什么、可以不看什么」,而非平铺全部数据。
3. **可追溯即可信** —— 条款引用、原始行号、规则版本始终可见。

## 约定
- **命名:** 后端 snake_case(Python);前端 React 组件 PascalCase、变量 camelCase;常量 / 环境变量 UPPER_SNAKE_CASE。
- **文件结构:** 通用框架层 `backend/core/` 与客户数据层 `tenants/` + `data/private/` 物理隔离(脱敏 = 删目录)。合成数据生成器 `backend/synth/` 为一等交付物。

## 关键原则
- 交付能解决用户故事的最简方案。
- 不确定必须显性化:AI 失败一律「转人工 + 显式标注」,绝不猜结论。能力声明机制(enabled/degraded/unavailable、available/inferred/missing)贯穿全系统 —— 系统不假装什么都知道,而是把不确定的部分显式摆出来交由人判断。
- 优化目标不是 F1,而是「在可接受的误拦预算下最大化召回」(漏放代价 >> 误拦代价)。
