# Product Requirements Document: ExpenseGuard MVP

## Executive Summary

**Product:** ExpenseGuard
**Version:** MVP (1.0)
**Document Status:** Draft — Ready for Technical Design
**Last Updated:** 2026-07-26

### Product Vision

把内部财务团队每月面对的数百至数千行报销数据,收敛成真正需要人看的少数几十行——并且每一条判定都附带可追溯的制度条款引用与原始数据行证据链。

ExpenseGuard 采用 **agent-in-workflow** 形态:主干是确定性 workflow(财务审计要求可复现、可审计),仅在「异常取证」环节使用真正的 ReAct agent。这一形态是产品定位的直接产物——审计结论必须经得起内审质询,因此不能把整条链路交给概率性推理。

### 定位:单一客户交付,按可推广的方式设计

**当前交付对象是内部财务团队,按生产系统标准建设。不是 SaaS 产品。** 不做自助注册、计费、租户管理后台,部署为单租户单机运行。

但设计上遵循一条原则:**所有本可以硬编码的地方——字段映射、规则阈值、制度条款——一律做成数据驱动,因为预期会有第二家企业。** 多租户是演进方向而非当前形态。

差异化能力锚定在研究阶段识别的三个空白:**跨单据/跨员工关联分析**、**可解释证据链 + 条款级逐字引用**、**制度文档自适应**。这三项在单客户场景下同样成立——制度会变、跨行异常单行看不出、内审要追溯依据,与客户数量无关。

### Success Criteria

MVP 成功 = 5 周内完成自有团队 dogfooding 全链路跑通:

- 处理 ≥1 个真实月度报销批次(数百行)
- 财务复核确认预审结果可用(而非「有趣但不能依赖」)
- 沉淀首批回流评测样本,建立漏放率与误拦率的初始基线

## Problem Statement

### Problem Definition

财务审核员每月面对数百至数千行报销数据,逐条人工审核在人力上不可行,但抽样审核又与该场景的**代价不对称结构**冲突——漏放一张违规单的代价(合规风险、内审问责、金额损失)远高于误拦一张合规单的代价(一次沟通成本)。这意味着优化目标不能是 F1,而应是「在可接受的误拦预算下最大化召回」。

三个具体的结构性困难:

1. **单行审核看不出的问题**:拆单规避审批阈值、发票连号、跨期跨部门重复报销、出差期间报销本地费用——这些异常只在**跨行关联**中显现。
2. **制度的时间维度**:制度频繁变更,2 月发生的费用必须按 2 月生效的制度版本判定,而非当前版本。
3. **结论的可核验性**:AI 给出的判定若无法追溯到条款原文与原始数据行,在内审场合等同于无效。

### Impact Analysis

- **用户影响**:审核工作量的绝大部分消耗在合规单据上;分级漏斗(确定性规则约 60% → 关联检测约 15% → 仅约 20% 需 LLM 判定)可将人工注意力重新分配到高风险项。*该 60/15/20 分布为研究阶段的架构设计假设,需用真实批次数据校准。*
- **对标影响**:研究阶段发现,中国费控领域几乎没有独立深度评测,厂商效果数字均为自述、无第三方验证。因此本项目不以外部对标为质量依据,而以自有复核数据建立内部基线。**本文档不对市场规模作任何量化断言。**
- **业务影响**:当前为内部交付,不做收入假设。是否推广至第二家企业,待本次交付的实测数据支撑后再评估。

## Target Audience

### Primary Persona: 财务审核员

**Demographics:**
- 企业财务岗,负责月度报销审核
- 技术水平中等:Excel 熟练,能理解规则配置,不写代码
- 每月处理数百至数千行报销记录,单次导入 500–5000 行

**Psychographics:**
- 风险规避型:最担心的不是多花时间,而是「漏放了一张违规单」
- 对 AI 判定持保留态度,除非能看到依据
- 习惯以 Excel 为工作载体

**Jobs to Be Done:**
1. **功能性** — 把数百行 Excel 收敛成真正需要人看的少数几十行,且每条判定附可引用的制度依据
2. **情感性** — 不再担心漏放违规单
3. **社会性** — 向管理层与内审证明审核结论有据可查、可复现

**Current Solutions & Pain Points:**

| Current Solution | Pain Points | Our Advantage |
|---|---|---|
| Excel 人工逐条/抽样审核 | 工作量不可持续;抽样与代价不对称结构冲突 | 全量确定性校验 + 分级漏斗,人力集中在高风险项 |
| 现有费控产品(汇联易、合思、每刻、分贝通、SAP Concur) | 单据级 OCR + 验真 + 基础合规已高度同质化;跨单据关联分析公开证据稀少(仅汇联易有明确案例);SAP Concur 官方社区明确承认跨员工图片级重复检测不支持;且引入需采购与实施 | 跨行关联分析 + 证据链输出;内部交付,私有化 |
| 上述产品的 AI 审核模块 | 「风险点+依据+建议」多为宣传口径,缺独立验证;制度自适应无端到端公开证据 | 条款级逐字引用 + 机械式引用校验 |

*上述产品事实均来自研究阶段的公开资料;厂商自述与第三方验证已在研究文档中区分标注。*

### Secondary Personas

- **规则配置员/管理员** — 配置限额阈值、白名单,导入制度文档与版本。核心诉求:改配置而非改代码。
- **财务负责人(只读)** — 查看汇总报告与风险分级,对内审/外审负责。核心诉求:结论可追溯。

**明确不在 MVP 内**:报销提交员工。系统无员工端界面,数据来源为报销系统的 Excel 导出。

## User Stories

### Epic: 带证据链的报销批次预审

**Primary User Story:**
"作为财务审核员,我想要上传本月报销 Excel 并在十几分钟内拿到一份按风险分级、每条判定都附制度条款引用的报告,以便把有限的人工精力集中在真正高风险的单据上。"

**Acceptance Criteria:**
- [ ] 支持 500–5000 行 Excel 导入,导入文件带版本管理,同一文件重复导入不产生重复结果
- [ ] 端到端处理 5000 行在 15 分钟内完成
- [ ] 报告按风险等级分级呈现,每条判定包含:命中的规则或制度条款 ID、条款逐字引用、触发该判定的原始数据行号
- [ ] 处理中断后可从断点恢复,已完成行不重复执行副作用

### Supporting User Stories

1. **"作为财务审核员,我想要系统按费用发生日自动匹配当时生效的制度版本,以便 2 月的费用不会被 5 月的新制度误判。"**
   - AC:制度文档入库时携带生效日期与失效日期;检索时以费用发生日作时间过滤条件;报告中标注所依据的制度版本号与生效日期

2. **"作为财务审核员,我想要看到跨行关联异常(拆单/连号/重复/时空冲突)及其证据链,以便发现单行审核看不出来的问题。"**
   - AC:支持四类关联检测;每个关联异常输出参与关联的全部行号与判定依据(如「阈值 5000 元,3 行合计 14,700 元,同一员工同一日同一供应商」)

3. **"作为财务审核员,我想要在复核台标记『确认违规 / 误报』,以便我的判断被记录并用于后续质量评估。"**
   - AC:复核台可对每条判定标记 confirmed / false positive;标记带复核人与时间戳,写入审计日志且不可静默修改

4. **"作为规则配置员,我想要以配置而非改代码的方式调整限额阈值与白名单,以便制度变更时无需研发介入。"**
   - AC:阈值与白名单以配置形式存储(非硬编码);配置变更留审计日志并记录版本;规则版本与判定结果关联,保证可复现

5. **"作为财务负责人,我想要每条 AI 判定都能追溯到条款原文与原始数据行,以便审核结论经得起内审质询。"**
   - AC:LLM 输出的条款引用须通过机械式校验(逐字引用与检索到的原文做字符串匹配),校验不通过则拒绝该引用而非原样呈现

## Functional Requirements

### Core Features (MVP — P0)

#### Feature 1: Excel 导入与文件版本管理

- **Description:** 接收报销系统导出的 Excel(500–5000 行),记录文件版本,支持同一批次重复导入的幂等处理。
- **User Value:** 无需改造现有报销系统即可接入;误操作重复导入不污染结果。
- **Business Value:** 无需改造现有报销系统即可接入;也是未来接入第二家企业时成本最低的一环。
- **Acceptance Criteria:**
  - [ ] 支持 .xlsx 导入,单次 500–5000 行
  - [ ] 每次导入生成 file_version_id,原始文件留存
  - [ ] 同一 file_version_id 重复处理不产生重复结果行(行级唯一键)
- **Dependencies:** 无
- **Estimated Effort:** S

#### Feature 2: Schema 映射与结构化解析

- **Description:** 将不同企业的 Excel 列名映射到内部统一字段模型,解析为结构化记录。
- **User Value:** 不同来源的导出格式无需人工整理即可处理。
- **Business Value:** 支撑「制度文档自适应」定位的第一环——接入新企业不改代码。
- **Acceptance Criteria:**
  - [ ] 支持列名映射配置,映射关系可保存复用
  - [ ] 解析失败的行进入错误清单并给出原因,不静默丢弃
  - [ ] 金额、日期字段完成类型归一化
- **Dependencies:** Feature 1
- **Estimated Effort:** M

#### Feature 3: 确定性校验

- **Description:** 限额、票种、时效、抬头、发票号查重五类硬规则校验,以配置化规则引擎(JSON Logic / 决策表)实现。
- **User Value:** 全量覆盖而非抽样,且结果完全可复现。
- **Business Value:** 承担分级漏斗第一层(设计假设约 60% 的拦截/放行判定在此完成),直接决定成本结构。
- **Acceptance Criteria:**
  - [ ] 五类校验全部实现,阈值与白名单为配置项
  - [ ] 相同输入 + 相同规则版本 → 相同输出
  - [ ] 每条命中记录规则 ID 与规则版本
- **Dependencies:** Feature 2
- **Estimated Effort:** M

#### Feature 4: 报告生成(含制度条款引用)

- **Description:** 输出按风险分级的审计报告,每条判定附条款引用与原始数据行。制度检索需支持按费用发生日的版本/生效日期过滤。
- **User Value:** 判定可核验,而非黑箱结论。
- **Business Value:** 这是三个市场空白中最核心的一个;也是对内审交代的基础。
- **Acceptance Criteria:**
  - [ ] 每条判定包含:规则/条款 ID、条款逐字引用、原始数据行号
  - [ ] 制度检索按费用发生日过滤生效版本,报告标注所用制度版本
  - [ ] LLM 产出的条款引用须通过逐字机械校验方可呈现
  - [ ] 报告可导出
- **Dependencies:** Feature 3;制度文档已入库(含生效日期元数据)
- **Estimated Effort:** L

#### Feature 5: 人工复核台

- **Description:** 高风险项进入复核队列,复核员标记 confirmed / false positive,结论留痕。
- **User Value:** 人在回路,AI 判定不是终审。
- **Business Value:** 复核结论是回流评测集的唯一真实标签来源,决定后续质量评估能否成立。
- **Acceptance Criteria:**
  - [ ] 按风险等级排序的复核队列
  - [ ] 复核界面同屏展示:原始数据行、判定理由、条款引用
  - [ ] 标记带复核人与时间戳,写入审计日志
- **Dependencies:** Feature 4
- **Estimated Effort:** M

### Should Have (P1)

| Feature | Rationale |
|---|---|
| 跨行关联检测(拆单/连号/频次异常/时间冲突) | 核心差异化,但依赖 P0 的结构化解析先稳定;统计方法先行,高召回挖候选 |
| 异常取证 Agent(ReAct 循环) | agent-in-workflow 的 agent 部分;在关联检测产出候选后才有输入 |
| 二维分级 | 需关联检测与取证结果作为输入维度之一 |

*P1 三项构成「统计挖候选 → LLM 取证定性」两阶段架构的完整闭环。若 W2 进度受阻,可先交付关联检测(统计层)而暂缓取证 Agent,报告降级为「标记候选待人工取证」。*

### Could Have (P2)

| Feature | Rationale |
|---|---|
| 复核结论回流评测集自动化 | MVP 可先手工导出复核结论;自动化是质量飞轮的加速器而非前提 |
| Trace 面板(Langfuse / Phoenix) | 结构化日志已能满足 dogfooting 期排查;面板提升效率但不阻塞交付 |

| 等保测评 | 合规要求写入非功能需求,但不做测评 |

## Non-Functional Requirements

### Performance

- **端到端处理:** 单次 5000 行 ≤ 15 分钟
- **断点续跑:** 处理中断后可从断点恢复,**已完成行不重复执行副作用**(行级幂等结果表 + checkpoint)
- **交互响应:** 复核台页面操作 < 2 秒(p95)
- **并发:** MVP 单租户单机运行,不设并发目标

### Security

- **多租户隔离:** 架构层预留(向量库 tenant 隔离 + 数据库 tenant_id),部署上单租户运行
- **数据脱敏:** 报销数据含员工个人信息;敏感字段在进入 LLM 前脱敏/令牌化
- **私有化(硬约束):** 向量库与模型层必须保留本地自托管路径,数据不出内网
- **审计日志:** 规则版本、判定依据、复核动作、配置变更全部留痕,支持复现
- **Prompt 注入防护:** 检索内容与指令分隔;结构化输出约束解码限制越界;promptfoo 红队测试
- **合规:** 遵循 PIPL 最小必要原则,明确数据留存期限与员工告知路径。*不做等保测评。*

### Usability

- **Accessibility:** WCAG 2.1 AA
- **Browser Support:** Chrome、Edge、Safari、Firefox 最新两个版本
- **Mobile Support:** 不适配。**桌面浏览器端 only**,不做响应式与平板优化
- **Internationalization:** 不适用(中文单语)

### Scalability

- **数据量:** 从数百行到数万行的扩展路径需在架构上留出(批处理 + checkpoint),MVP 实测上限 5000 行
- **租户:** 单租户 → 多租户的隔离方案在架构层内建(metadata filter 起步,关键租户可升级独立 collection)
- **向量规模:** 10 万级向量为设计目标

## UI/UX Requirements

### Design Principles

1. **证据优先于结论** — 任何判定在界面上都与其依据同屏呈现,不需要额外点击才能看到理由
2. **分级引导注意力** — 界面结构服务于「先看什么、可以不看什么」,而非平铺全部数据
3. **可追溯即可信** — 条款引用、原始行号、规则版本始终可见,不因界面简洁而隐藏

*具体设计系统与视觉方案留待 Technical Design 阶段;MVP 使用现成组件库快速搭建。*

### Information Architecture

```
├── 登录
├── 批次列表(Dashboard)
│   ├── 导入新批次
│   └── 历史批次(按文件版本)
├── 批次详情
│   ├── 处理进度 / 断点状态
│   ├── 分级报告
│   │   ├── 单行判定(含条款引用)
│   │   └── 跨行关联异常(含参与行与证据链)
│   └── 报告导出
├── 复核台
│   ├── 待复核队列(按风险等级)
│   └── 复核详情(原始行 + 判定理由 + 条款引用 + 标记)
└── 配置
    ├── Schema 映射
    ├── 规则配置(阈值 / 白名单)
    └── 制度文档管理(版本 + 生效日期)
```

### Key User Flows

#### Flow 1: 批次预审(主流程)

1. 上传 Excel → 2. 系统生成 file_version_id 并校验列映射 → 3. 判定:映射完整则直接解析;否则进入映射配置界面补全 → 4. 确定性校验 + 关联检测 + 取证 → 5. 生成分级报告 → 6. 审核员查看报告,高风险项进入复核队列

#### Flow 2: 人工复核

1. 打开复核台 → 2. 按风险等级取待复核项 → 3. 同屏查看原始行、判定理由、条款引用 → 4. 判定:标记 confirmed 或 false positive → 5. 结论写入审计日志并计入回流样本池

#### Flow 3: 制度版本更新

1. 管理员上传新版制度文档 → 2. 填写生效日期与失效日期 → 3. 系统按条款边界切分并入库 → 4. 判定:若与既有版本时间区间冲突则提示确认;否则直接生效 → 5. 后续批次按费用发生日自动匹配对应版本

#### Flow 4: 中断恢复

1. 处理过程中断(进程退出 / 手动停止)→ 2. 重新触发该 file_version_id 的处理 → 3. 系统查询行级结果表 → 4. 判定:已完成行跳过;未完成行从 checkpoint 继续 → 5. 处理完成,无重复副作用

## Success Metrics

本项目的成功指标以**审核质量**为主,而非常规增长指标——交付对象为内部财务团队,DAU/MRR 类指标不适用。

| Category | Metric | Target | Measurement |
|---|---|---|---|
| 质量(核心) | 漏放率对应的召回下限 | ≥ 95% | 对**被放行样本**随机抽样人工复核,估算漏放 |
| 质量 | 误拦率上限 | ≤ 20% | 复核台标记为 false positive 的占比 |
| 效率 | 人工复核工作量下降 | ≥ 50% | 需人工查看的行数 / 总行数,对比现有全量人工审核 |
| 成本 | 每千行处理成本 | 可测算且有归因 | trace 按 task 聚合 token / 延迟 / 成本 |
| 激活 | 完成 ≥1 个真实月度批次全链路 | 1 个批次(数百行) | 批次记录 |
| 参与 | 复核台标记覆盖率 | 高风险项 100% 被复核 | 复核队列完成率 |
| 留存 | 团队连续使用月度批次 | 连续 2 个月 | 批次导入记录 |
| 收入 | 不适用 | — | 内部交付,无商业化 |

> **关于指标数值的重要说明:** 95% / 20% / 50% 均为**初始假设阈值**,用于设定工程目标,不是有依据的行业基准。研究阶段已明确:审计与反欺诈领域**未找到可直接套用于本场景的可信公开误报率数据**。这些阈值必须用自有复核数据标定,并采用代价敏感 / Neyman-Pearson 方法(固定可接受误拦率上限,在此约束下最小化漏放),而非按 F1 优化。

> **采样偏差警告(工程必读):** 若只标注被拦截样本,将无法评估漏放率——这是信用评分领域的 reject inference / selection bias 问题。因此**从第一个批次开始就必须对被放行样本做随机抽检**,否则「召回 ≥95%」这一核心指标在数学上不可测量。

## Constraints & Assumptions

### Constraints

- **Budget:** 灵活,无硬性上限;但需建立每千行成本估算模型
- **Timeline:** 5 周 —— W0 立项 + W1–W3 开发 + W4 上线与文档
- **Resources:** 5 人团队,全职,5 周内无并行事项
- **Technical:**
  - 语言 Python
  - 模型以国产模型为主(DeepSeek / 通义 / 智谱 / Kimi)
  - **私有化部署是硬约束**:向量库与模型层必须保留本地自托管路径
  - 部署形态:Docker Compose 单机实跑 + 结构化日志 + trace 面板 + 健康检查 + 优雅退出
  - 技术选型已在研究阶段确定(LangGraph / Qdrant / JSON Logic / 两阶段检测 / Langfuse 或 Phoenix / 分级漏斗)

### Assumptions

- **用户假设:** 财务审核员愿意在看到条款引用的前提下信任 AI 预审结论;首个用户是自有团队,反馈回路短
- **能力假设:** 跨单据关联分析 + 可解释证据链 + 制度自适应是本项目的核心价值。*研究阶段确认现有产品在这三项上公开证据稀少,但「公开证据稀少」不等于「能力缺失」——存在信息不完全风险*
- **技术假设:**
  - 分级漏斗分布约为 60% 确定性规则 / 15% 关联检测标记 / 20% 上 LLM(**设计假设,需实测校准**)
  - 国产模型的 function calling 与结构化输出在约束解码兜底下足够稳定(需 W0 实测验证)
  - 制度文档可按条款边界有效切分
- **项目假设:**
  - 5 人全职、5 周内无并行事项
  - 无外部硬性截止日,W4 末为内部交付节点
  - 真实报销数据与制度文档在 W0 内到位
  - 交付对象为内部财务团队,5 周内无第二家客户

### Open Questions

- 分级漏斗的真实分布是多少?60/15/20 的设计假设需要第一个真实批次来校准

- 误拦率上限 20% 是否是财务团队可接受的心理阈值?需 dogfooding 首轮反馈确认
- 制度文档的实际结构化程度如何?若条款边界不清晰,chunking 策略需调整 —— 待 W0 拿到真实文档后评估
- 回流评测集达到多少样本量才足以支撑阈值标定?**TBD**
- 时间冲突检测所需的出差申请数据是否可获取?若报销 Excel 中无行程信息,该检测能力受限 —— **TBD**
